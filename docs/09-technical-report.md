# 09 · 技术报告（Technical Report）

> 论文式结构，便于评审快速判断项目的**问题—方法—结果—局限**。
> 完整实现见仓库代码；本文档中的数字来自本项目的实测与内置合成数据，逐项标注来源。

## 摘要

校园跑类运动打卡应用把跑步成绩与学分绑定，作弊动机强、手段门槛低。本文以华中大体育（`net.crigh.hzkjsport`
v1.1.0）为案例，提出并实现了一套**红蓝对抗测试床 + 分层防护参考实现**：攻击侧覆盖三种主流作弊路径
（无 root 注入重打包、虚拟机+虚拟环境、容器虚拟环境），防护侧给出客户端检测与服务端交叉校验的可运行参考实现，
并以"攻击向量 × 防护层"矩阵量化各层的有效性。实测发现：壳的入口 dex 完整性校验能挡住重打包路线；
而容器路线之所以可行，根因是目标应用**缺少运行环境真实性校验**；服务端"步频×速度"交叉校验是对抗定位伪造的关键防线。

## 1. 引言

校园跑（如华中大体育、各类高校体育打卡 App）通常要求学生在规定时段内完成一定里程，成绩计入体育课或评优。
这类应用的核心可信度依赖三件事：位置真实、运动真实、身份真实。而移动端的三个现实使三者都脆弱：
定位可被系统 mock 或 SDK 层注入替换；传感器数据可被注入；运行环境可被虚拟化（模拟器/容器）。

现有防护多集中在客户端单点（isMock、包名黑名单、壳完整性），缺少系统化评估。
本文的贡献是：

1. 三种攻击路径的可复现测试床（软件形态）；
2. 五层防护参考实现（客户端 + 服务端），以"可量化"为设计目标；
3. 一个真实案例的对抗评估矩阵，指出"最弱一环"与最高性价比的加固点。

## 2. 威胁模型（摘要）

- 攻击者能力：安装/重打包应用、控制虚拟环境、注入 hook；不掌握服务端与密钥
- 攻击目标：让伪造成绩通过校验（而非窃取数据）
- 不在范围：服务端漏洞利用、账号买卖、真实账号批量操作

## 3. 方法

### 3.1 攻击侧（三种路径）

| 路径 | 关键动作 | 关键约束 |
|---|---|---|
| A 注入重打包 | apktool 改写 + Gadget 加载 + SDK 层 hook | 触发壳完整性校验（入口 dex tamper） |
| B 虚拟机 | redroid/模拟器 + frida-server + 传感器伪造 | 暴露模拟器指纹；无需改包 |
| C 容器 | 双开/VMOS/VirtualApp 内运行 + 容器内 hook | 无需改包、无需 root；依赖目标未做容器检测 |

### 3.2 防护侧（五层）

0 设备与环境（反 mock/注入/模拟器/容器 + 完整性）→ 1 采集加固（native 计算 + HMAC）→
2 上报通道（签名/nonce/时间窗）→ 3 服务端真实性（轨迹物理、地图匹配、步频×速度、环境一致性）→
4 群体行为（轨迹指纹、相似度聚类）→ 5 证据链与阶梯处置（心跳、抽查、人脸活体）。

## 4. 评估与结果

### 4.1 真实案例观察（华中大体育 v1.1.0）

| 观察 | 结果 | 来源 |
|---|---|---|
| 重打包后启动 | `RuntimeException: entry classes.dex is tamper`，进程终止 | 真机实测（Android 15，realme） |
| 壳体系 | DA2Lock + libjdi VMP，解密 dex 落盘 `dsn0/dex/libdsn_*.jar` | 静态 + logcat 分析 |
| 运行时检测 | XposedBridge / su 执行 / fakelocation 包名（每页 onResume）/ frida 字符串 | logcat 与字符串分析 |
| 业务判定 | 超速段剔除、步频异常=自行车、距离过短拒提交、人脸核验 | 字符串/音频/logcat 反推 |

### 4.2 防护参考实现的合成数据验证

- `trajectory_plausibility.py --demo`：正常轨迹 → `ok`；脚本匀速轨迹 → `reject`（超速点占比 >20% 升级）；
  重放轨迹 → `reject`（轨迹哈希/相似度命中）
- `run_evidence_validator.py --demo`：正常样本 100 分 pass；骑车样本命中 `SUSPECT_VEHICLE`；
  虚拟环境样本 32 分 reject

> 说明：上述为**合成数据**上的规则验证，不等价于真实分布上的召回率/误报率；真实基准集列入 roadmap。

### 4.3 对抗矩阵（定性，详见 docs/05）

关键结论：客户端单点检测可被绕过；壳完整性是有效的第一道硬门槛；服务端交叉校验是决定性防线；
容器路径（C）是目标当前最薄弱的环节。

## 5. 讨论与局限

1. **样本局限**：单案例（一个 App 的一个版本），结论外推需谨慎
2. **数据局限**：尚无大规模真实作弊样本，召回/误报指标待补
3. **伦理与合规**：攻击侧仅用于授权环境；防护侧以最小采集、限期删除为原则
4. **对抗升级**：任何单层检测都可能被针对性规避，需持续评估（本项目提供评估框架而非一次性补丁）

## 6. 结论

校园跑类应用的安全评估应把重心从"客户端单点检测"转向"服务端持续性交叉校验 + 分层证据链"。
本项目提供的三方式测试床与五层防护参考实现，可作为学校与厂商的评估基线。
