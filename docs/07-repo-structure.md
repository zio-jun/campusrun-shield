# 07 · 开源组织结构（怎么把这个项目"搞成开源"）

> 定位：**一个仓库、两件交付物、三种攻击方式**。
> 攻击端是"软件"（可执行 CLI），防御端是"参考实现库"（可集成、可验证，不是独立 App）。
> 报名时按「原创开源软件 · 工具软件」申报，防护库作为项目的一部分呈现。

## 1. 产品结构

```
                        campusrun-shield（一个仓库）
        ┌──────────────────────────────┬──────────────────────────────┐
        │  ① 攻击测试床（软件）          │  ② 防护参考实现（库）          │
        │  campusrun-attacker.py CLI    │  validate_cli.py + 校验器/检测 │
        │  ├─ 方式 A 本机注入            │  ├─ server-side  轨迹/证据     │
        │  ├─ 方式 B 虚拟机              │  ├─ client-side  反mock/完整性 │
        │  └─ 方式 C 容器虚拟环境        │  └─ native       指标签名      │
        └──────────────────────────────┴──────────────────────────────┘
                              ↓ 共同支撑
                  docs/（威胁模型→攻击→防护→评估）+ evaluation/
```

边界原则：
- **攻击端**只解决"如何构造可复现的攻击路径"，不绑定具体第三方账号，参数全部占位/可配置；
- **防御端**只解决"如何在客户端/服务端识别与处置"，不提供可直接攻击生产系统的利用链；
- 两侧共用案例数据（华中大体育实测结论），形成闭环评估。

## 2. 目录规范

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| `docs/` | 设计与评估文档，编号顺序即阅读顺序 | 代码、二进制 |
| `offense/` | 攻击 CLI、各方式脚本、环境编排 | 真实密钥、他人账号 |
| `defense/` | 校验器、检测模块、native 示例 | 与攻击无关的业务代码 |
| `evaluation/` | 对抗矩阵、指标、基准数据 | 未脱敏日志 |
| `submission/` | 参赛佐证材料（docx 生成脚本） | 平台模板原件 |

## 3. 版本与发布

- 语义化版本：`v0.1.0` = 文档+攻击 CLI+防护库骨架；`v0.2.0` = 三方式补全+评估数据；`v1.0.0` = 完整闭环
- 每次发布附：变更说明、可复现命令、已知限制
- 首版当前进度：方式 A/B/C 文档与脚本齐备；B/C 走 frida-root 路线无需重打包，是不触发壳校验的可执行路径

## 4. 社区与贡献

- `CONTRIBUTING.md` 已定义提交规范与边界（仅授权评估）
- Issue 模板建议：Bug / 新检测规则 / 文档改进
- 不接收：针对真实账号的利用代码、未脱敏用户数据、第三方密钥
- 评审视角：原创性（自研测试床+防护）、实用性（可复现、可量化）、社会价值（防作弊保护）
