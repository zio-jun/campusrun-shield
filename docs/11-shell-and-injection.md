# 11 · 壳与注入对抗实录（每一招 → 每一破法）

> 从一次完整的加固壳对抗实验（62 个改造版本迭代）中沉淀的攻防记录。
> 每条以「攻击动作 → 壳的响应 → 攻方再破法 → 防御建议」四段式展开。
> 目标壳：商用 VMP 加固（DxShield v5 系列），本仓库不做具体厂商指向，重点在通用结论。

## 1. 签名与包体校验链

### 1.1 重签名必然触发什么
- 实测：重建 + 重签后，壳不立即崩溃，而是在**请求时刻**经 VMP 调度器做校验，失败后自刀（`kill(pid,9)` + 兜底抛异常 → `EXIT_SELF`）。
- 攻方响应 a：hook `getPackageInfo` 返回原证书（sig-spoof）。
- 攻方响应 b：hook libc `open/openat`，把壳对 `base.apk` 的读取重定向到原版 apk 副本 + 伪造 `stat.st_size`。
- 壳侧防御升级建议：
  1. 校验读取改走内存映射（mmap 自身文件），重定向攻击失去载体；
  2. 校验用「实际读取字节数」而非 st_size；
  3. 校验失败不立即崩溃，先**静默上报设备指纹**再延时自毁（防崩溃点被定位）；
  4. 把校验结果混入解密密钥派生——被 NOP 后功能自毁而非放行。

### 1.2 加密资产（dex 密文）的尺寸陷阱
- 实测：篡改加密资产使其尺寸 +89 字节 → 壳直接 `EXIT_SELF`。尺寸校验存在且有效。
- 攻方响应：不重编译 dex，改为**同尺寸字节补丁**（原始 jar 条目为 STORED 无压缩时可行）。
- 防御建议：**只校验尺寸是不够的**。必须内容哈希；且把 jar 条目改为 deflate 存储，使等长补丁也会改变压缩输出尺寸；最后把哈希与解密密钥绑定。

## 2. 解密落盘与"防删"对抗

### 2.1 落盘窗口
- 壳流程：解密 csn → 写 `/data/user_de/…/dsn0/dex/libdsn_<hash>.jar` → DexClassLoader 加载 → 删除。
- 攻方：hook `File.delete` + `unlink`/`unlinkat`，删除前抢拷贝（即"防删偷存"）。
- 防御建议：优先 `InMemoryDexClassLoader`；必须落盘则 O_EXCL + 用完即 unlink + 目录 0700；文件名哈希加启动随机盐。

### 2.2 状态污染（防御方意外获益）
- 实测：早期失败运行遗留**截断的 jar**，因文件名哈希固定，后续启动复用坏文件 → `DexFile.openDexFileNative: Invalid file` → 应用启动即崩。攻击方被自己的脏状态卡死数小时。
- 防御建议：落盘文件使用前校验魔数与长度；启动时清理临时目录；文件名哈希随机化（让"固定文件名复用"失效）。

## 3. 多进程守卫与自刀

### 3.1 守卫模型
- 壳行为：主进程 + 守卫进程；检测到篡改后 `kill(self, SIGKILL)`；被拦后抛 Java 异常走 `EXIT_SELF` 兜底。
- 攻方：hook `kill/tgkill` 屏蔽信号；hook 守卫线程入口类（`_me_.a` 类名级别）让其空转。
- 防御建议：
  1. 自刀用 `syscall(SYS_kill)` 直调，绕过 libc 符号 hook；
  2. 守卫与主进程双向心跳：任一方死亡，另一方延时自毁或上报；
  3. 校验结论冗余三份（Java/native/跨进程）互相印证，hook 其一仍被其余识破。

### 3.2 JNI 异常吞吃
- 攻方：改 JNIEnv 函数表 `ThrowNew` 表项（偏移 14×指针宽度），吞掉篡改异常。
- 防御建议：启动时校验 JNIEnv 表关键项落在 libart 段内；关键异常路径改用返回值错误码 + 独立自毁线程，不依赖 JNI 异常传播。

## 4. 注入面实录

### 4.1 Gadget 改名注入（低特征）
- 攻方：libgadget.so 改名 `libcampusrun.so`，config 同改名，smali 自提取脚本到 files/，脚本模式零端口。
- 防御：maps 模块白名单、内存字符串扫描（frida/gum/gadget 特征，即使改文件名）、lib 目录官方签名清单、加载时序异常检测。

### 4.2 ClassLoader 钩子递归陷阱（攻方自爆实录）
- 攻方第一方案：hook `java.lang.ClassLoader.loadClass/findClass` 捕获业务 loader。
- 结果：壳自定义 findClass（解密）在 super 链上与被替换基类方法互相调用 → **栈溢出，应用秒闪退**（两版连炸）。
- 结论：**自定义 findClass 的壳天然反基类 hook**。防御方可以主动加深这个结构（loader 内再包一层代理）。
- 攻方修正：改 hook `DexClassLoader.$init`（构造器）、`Instrumentation.callApplicationOnCreate/newApplication`、`Application.onCreate` 四个事件点捕获 loader，全部零递归。

### 4.3 枚举挂死（环境自伤）
- 实测：`Java.enumerateClassLoaders` 在目标 ART + 壳组合下**间歇性挂死**注入脚本线程（多次成功枚举后，某次调用冻结事件循环）。
- 防御建议：应用侧保持类加载路径稳定即可维持这种不确定性；日志埋点监测"攻击脚本静默"。

### 4.4 同步 IO 卡死脚本线程
- 实测：注入脚本启动后同步遍历 `/data/user_de`、`/sdcard/Android/data` 等 FUSE/无权限目录 → 事件循环冻结，所有定时器（含心跳）停摆。
- 防御建议：目录权限设计（无法列目录 ≠ 安全，但能耗尽攻击脚本稳定性）；核心逻辑不依赖攻击脚本稳定性——防御永远假设注入存在。

## 5. 校验时序与"延时启用"的攻防

- 攻方：open 重定向延时 25s 启用，避开壳启动期自身读取，只在请求时刻生效。
- 防御建议：壳自身读取与校验读取**交错分布**在启动后随机时刻，让"延时启用"窗口不可预测；请求校验与启动校验用两套独立路径（攻击者骗过启动校验后，请求校验仍触发）。

## 6. 防御方检查清单（针对本类攻击）

- [ ] 签名校验取真值（native/binder 侧），不依赖 Java 返回值
- [ ] 自身 so/资产内容哈希（非尺寸）校验
- [ ] 解密密钥与资产哈希绑定
- [ ] 业务 dex 内存加载优先；落盘防删 + 随机盐
- [ ] 自刀走 syscall 直调；校验结论多路冗余
- [ ] 守卫双向心跳；心跳缺失上报服务端
- [ ] maps/字符串/JNI 表/加载时序 四类注入检测
- [ ] 校验失败静默上报 + 延时自毁，不即时崩溃
