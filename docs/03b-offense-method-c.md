# 03b · 攻击方式三：应用级虚拟环境（双开 / VMOS / VirtualApp 容器）

> 一句话：**目标 App 的环境检测缺失时，可以直接把它塞进"虚拟空间"里运行**，
> 在容器内完成 hook 与定位伪造——不需要重打包、也不需要真机 root。
> 这条路径能成立，根因不是容器技术多强，而是**目标应用的运行环境真实性校验做得敷衍**。

## 1. 原理

应用级虚拟环境（App Virtualization）：宿主 App 通过 VirtualApp 类框架在自己的进程里加载并运行目标 APK——
常见形态包括「双开助手/多开分身」「VMOS / VPhone 等虚拟安卓」「太极/容器化 hook 方案」。
目标 App 以为自己运行在独立设备上，实际跑在容器提供的虚拟文件系统、包管理、传感器与定位服务之上。

```
真实手机
└── 容器 App（双开助手 / VMOS / VirtualApp 派生）
      ├── 虚拟包管理：加载目标 APK（同进程/独立沙箱）
      ├── 虚拟文件系统：/data/data/<容器>/virtual/...
      ├── 虚拟服务：定位、传感器、相机可被容器拦截
      └── hook 层：Xposed 模块 / 进程注入 / 容器自带能力
            └── 目标 App  →  定位虚拟层（复用方式一的 hook.js）
```

## 2. 可行性根因：目标应用的环境检测缺失（设计缺陷）

方式三能成立的根因是目标 App **只做了客户端壳的静态完整性校验（dex 校验），
却没有做运行环境真实性校验**：

- 未检测 VirtualApp/容器特征：包名、进程可执行路径（`/data/data/<容器>/virtual/...`）、
  容器类名与 SO 特征
- 未做多开/分身检测：同 UID 多进程、双开标志、包管理器异常
- 未校验安装来源与签名链、设备指纹一致性
- 壳的安全机制对"APK 完整、但运行在容器里"这一状态完全没有感知

换句话说：**壳守住了"安装包没被改"，却没守住"运行环境是真实的"**——这就是敷衍之处。

## 3. 攻击能力对比

| 能力 | 方式一 注入重打包 | 方式三 容器内运行 |
|---|---|---|
| 需要重打包 | 是（触发 dex 完整性校验） | **否** |
| 需要 root | 否 | 否（容器自带权限模型） |
| 定位伪造 | SDK 层 hook | 容器系统层 mock + SDK hook 双路径 |
| 传感器伪造 | 否 | 视容器能力（VMOS 类可注入） |
| 批量/快照 | 否 | **是**（容器实例可复制、快照回滚） |

## 4. 被检测点（补上防护后即可拦截）

1. **虚拟空间特征**：VirtualApp 类名/包名、进程路径、`/proc/self/maps` 中的容器 SO
2. **多开检测**：同 UID 多进程、双开标志、`/proc/<pid>/cmdline` 异常
3. **环境完整性**：安装来源、签名链、设备指纹一致性
4. **定位来源一致性**：容器内系统 mock 结果 vs SDK 层结果偏差
